## 结论先行

**Tool** 是 Agent 调用的外部能力单元：检索、代码执行、数据分析、数据库查询、邮件、Slack 等。模型负责「选哪个、填什么参数」；**真实副作用发生在工具执行面**。

没有工具的「Agent」大多只是会多步说话的聊天机器人。

---

## 是什么

完整架构中，核心循环的 **Action** 选择工具，**Action Input** 准备参数，再进入执行。图中常见工具类型：

- 浏览器 / 搜索  
- 代码执行  
- 数据分析  
- 数据库查询  
- 邮件 / Slack 通知  

工具应具备：清晰名称与描述（供模型选择）、输入 schema、错误返回、权限边界。

---

## 应用场景

| 场景 | 工具例子（中性） |
|---|---|
| 调研 | 网页检索、文档读取 |
| 办公闭环 | Slack / 邮件发送 |
| 数据核对 | 只读数据库查询 |
| 报告 | 写文件、生成表格 |

---

## 效益

| 效益 | 说明 |
|---|---|
| 扩展能力边界 | 超越参数内知识 |
| 可审计 | 每次调用可记日志 |
| 可门禁 | 按工具名 / 参数做策略 |

---

## 设计要点

1. **描述质量**直接影响选错工具的概率  
2. **失败信息**应机器可读，便于 Reflection  
3. **权限**：只读 vs 有副作用要分级（本仓门禁章）  
4. **与 MCP**：工具可由 MCP 服务器暴露，见 [mcp.md](mcp.md)

---

## 与本仓挂钩

LangChain 擅长工具 / 模型适配；pi / dsh 提供 tool loop 运行时；平台层需叠加 scope 与不可逆审批，避免「模型想调就能调」。
